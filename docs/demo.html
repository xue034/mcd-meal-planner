四、怎么用

热量模式（默认）

$ python planner.py --kcal 800 --protein 30
→ 巨无霸 513 + 雪菜脆笋鸡肉粥 120 + 卡布奇诺中杯 167
→ 合计 800 kcal（偏差 0）· 蛋白 40g · 钠 1601mg

控钠模式（差异化核心）

$ python planner.py --kcal 800 --sodium-limit 1200 --sodium-focus
→ 麦乐鸡4块 170 + 大薯条 379 + 可乐大杯 224
→ 合计 773 kcal · 钠 553mg（上限的46%）

钠密度模式（避开高钠陷阱）

$ python planner.py --kcal 800 --density-focus
→ 按 mg/100kcal 排序，优先避开粥类、鸡翅等高密度单品

高钠报告 / JSON 输出

$ python planner.py --kcal 800 --sodium-report    # 高钠陷阱预警
$ python planner.py --kcal 800 --json            # 可编程输出

五、为什么用 TOON 解析器

麦当劳 MCP 的 list-nutrition-foods 不返回标准 JSON，而是返回 TOON（Token-Oriented Object Notation）—— 为降低 LLM Token 消耗设计的紧凑行格式。直接用 json.loads() 会抛异常。

[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  巨无霸,null,2146,513,27,26,42,961,171
  中薯条,null,1210,289,4,12,38,165,18
格式规则：首行 [N]{字段列表}: 声明记录数与字段名，后续每行一条记录，逗号分隔，null 表示空值。

本项目实现了完整解析（toon_parser.py），含空行跳过、注释忽略、字段缺失补齐、往返转换校验。这是接入此接口最容易踩的坑，代码开源可直接复用。

七、这个项目刻意不做的事

不调用 query-nearby-stores——实测该接口对未收藏门店的用户返回 600050 收藏餐厅列表为空，两次不同参数稳定复现。依赖它的方案在真实用户场景下会直接失败。本项目主动放弃「就近门店」能力，换取在所有用户场景下稳定可用。
不接入下单链路——本项目是营养规划工具，不介入交易流程，避免误下单风险。
